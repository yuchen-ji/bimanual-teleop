# 厂家 drag 模式双腕上转排查（2026-10-23）

用户报告：双臂新增六维力传感器及灵巧手，通过程序做过负载标定；在厂家软件切入 drag 后、尚未按末端拖动按钮时，最后一个关节即向上转动且力很大。

## 已确认的证据

- 使用固定版本 SDK 的独立 `RecvFile` 文件入口，经 TCP 10240 只读下载控制器工具表、`robot.ini` 和日志。没有建立机器人控制连接，没有清错、使能、切模式、松闸、下发目标或写入参数。
- 控制器 `/home/fusion/tools_cfg.json` 中 `current_tool.arm0=null`、`current_tool.arm1="tool-1"`；两侧所有工具的十项动力学参数全部为零。该文件与本机 `TJ_FX_ROBOT_CONTRL_SDK/MarvinPlatform_EN/tools_cfg.json` 的 SHA-256 相同。
- 项目 `configs/tianji_teleop.yaml` 中的左右工具质量分别为 1.079348 kg 和 1.233148 kg，法兰坐标系下质心分别为 `[63.858565,39.662969,166.953365]` mm 和 `[19.124213,5.423994,105.129211]` mm。尚未确认这些历史结果是否包含当前安装的全部工具。
- 项目 `ControlSDK.configure()` 只下发运行参数，驱动核对 `m_In.m_ToolDyn` 回读；没有更新厂家工具表。因此程序标定或项目配置中有数值，不能证明厂家软件的当前工具已应用同样的参数。
- 本地厂家上位机 `ui_EN.py` 的连接流程从控制器下载工具表；约 6848 行以 `if/elif` 读取左右工具名。一侧未选择时，另一侧的有效选择也可能未加载。本次工具表恰好为左侧未选择。该源码缺陷是否对应用户使用的具体厂家软件版本，仍需确认。
- 上位机 drag 切换代码没有显式发送当前实测关节角，但控制器日志明确记录进入扭矩模式时 `Sync cmd pos as actual feedback pos`。因此不能仅凭上位机缺少该调用，认定旧位置目标造成此次上转。
- 控制器两臂重力分别为 `[0,+9.81,0]`、`[0,-9.81,0]`，与项目固定 M6 模型一致；这不代替对实体安装方向的核实。

## 判断与限制

已经确认程序负载配置与厂家持久化工具表不一致，应优先修正负载应用链路。但工具表不是实时反馈，当前无法确认故障瞬间实际生效的 `m_ToolDyn`，也没有此次切换前后的关节目标、实测角度及力矩序列，尚不能唯一确定向上旋转的原因。

静止时持续主动转动，需要区分错误的重力补偿（含质量、质心及坐标系错误）、关节扭矩反馈零偏，以及阻抗位置误差。负载缺失本身不能充分解释上转方向。新增腕部六维力传感器的去零，也不能代替机器人 J7 关节扭矩传感器的标定。

下载日志包含历史启动和模式切换记录，没有 `drag` 字样；控制器时钟未与主机同步，不将其中某次切换直接认定为用户报告的本次异常。独立下载 `/home/fusion/tool_dyn_kine.txt` 返回失败，未取得有效内容。

## 处理顺序

1. 先停止有明显主动上转的 drag 尝试。核对当前组合的负载辨识结果是否包含传感器、转接件、灵巧手等全部法兰外负载，且辨识空载/带载基准与最终安装一致；不含则重新辨识。若采用空载/带载差分辨识，而空载采集时已装上传感器，结果可能只包含后加的部件，需核对辨识程序的具体约定。
2. 在厂家软件中分别选择左右工具，导入对应完整十项辨识输出，按 SDK 约定保留参数顺序、单位和法兰参考系，执行设置和保存。不要只更新项目 YAML，也不要只修改显示值。
3. 在不使能运动的条件下，回读两侧 `m_In.m_ToolDyn`，与辨识结果逐项核对；断开重连后再次确认，验证厂家工具配置可恢复。仅检查 JSON 或设置调用返回值不够。
4. 由现场人员在可控条件下单臂验证 drag，记录切换前后的 `cur_state`、`imp_type`、`drag_sp_type`、`tip_di`、`fb_joint_cmd`、`fb_joint_pos`、J7 扭矩及外力矩估计，确认实体上转实际对应 J7 还是腕部其他轴。关节 drag 应配关节阻抗，切换拖动类型先退出原模式。
5. 如果负载回读正确、目标与实测位置一致仍上转，再请厂家核查 J7 扭矩传感器的零偏/方向及控制器补偿。不要通过清编码器零点或盲调补偿消除现象。
