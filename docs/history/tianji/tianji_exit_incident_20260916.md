# Q 退出后左臂异常运动：排查与退出流程修复（2026-09-16）

用户报告：遥操作正常，按 Q 退出后左臂持续大范围转动；无其他控制程序。按实体急停后停止，随后已释放急停。

## 修复前已确认的代码缺陷

1. `TeleopUI.handle("q")` 调用 pause 后退出。Cartesian 停止经 `tj_hold` 调用 SDK `OnSetStopRunning`。
2. SDK 在所选臂的低速标志为 1 时直接返回 true，不发送 RSTA 停止请求。
3. 低速标志为 0 时，SDK 对 RSTA 最多尝试三次，但即使控制器三次拒绝仍返回 true，桥接据此返回成功。
4. Python 驱动关闭时只等待待重试的停止请求，不等待成功返回后的停稳确认。没有新反馈确认也会释放连接。未确认事件仅发往可选 sink；默认遥操作 sink=None，用户看不到该事件。
5. `OnRelease` 释放线程和套接字，并不下发去使能。主机看门狗随进程结束，不能保护退出后的控制器运动。

## 离线复现

使用当前动态库及本机 127.0.0.1 模拟控制器；没有连接实机。复用原生测试中的 LoopbackController、反馈模式 3 / 阻抗类型 2：

```text
cartesian_low_speed: hold_return=0, stop_packets=0
cartesian_moving: controller_rejection=1, hold_return=0, stop_packets=3
```

第一项证明“停止成功”可以对应零条停止请求；第二项证明停止被拒绝仍返回成功。临时复现源码：`/tmp/tianji_exit_stop_repro.cpp`。该首次复现阶段没有改动或重建在用控制代码，也没有发送任何实机命令；后续修复见下文。

## 结论边界

这些缺陷足以否定“程序退出表示机器人已安全停止”的假设。后续已取得控制器日志（见下文），但缺少退出瞬间的主机反馈和发送记录，不能断言当时实际走了哪一条分支，也不能仅凭此确定左臂持续大幅转动的控制器内部原因。先前回位/取消及 Hand2 保持测试没有覆盖笛卡尔阻抗遥操作退出后的安全停机。

## 本次修复

- 补齐上一任务未接完的 ABI 4 接口。`tj_hold` 绕过 SDK 低速跳过和拒绝仍成功的封装，真实返回 RSTA 结果。
- Q、Ctrl+C、EOF 及运行异常的清理路径直接关闭运行模块；机械臂关闭不再先调用 pause/RSTA。联合运行先关闭机械臂，再释放手部，保留两侧清理错误。
- 驱动记录本会话尝试控制过的臂。退出关闭标记阻止后台接合、回位和看门狗再发暂停或运动指令；已暂停、已完成回位的臂也请求下伺服。单臂操作只处理对应侧；只读会话不下发停机。
- `tj_disable` 取消尚未发出的旧目标，发送仅含 state=0 的下伺服报文。等待发送成功及各臂新的 IDLE/低速反馈，确认条件见桥接 README；接收线程在此期间保持工作。
- 最多等待 2 秒。发送失败、丢反馈、过期/不推进的反馈、仍在 TORQUE/ERROR、非低速或无效速度均不算成功。失败显示默认可见的实体急停提示、抛出异常并以非零退出码结束；释放连接不被当作停机确认。
- 退出不自动清错、使能、回位或替换关节目标。下伺服不是实体急停替代品，断网、强杀进程和控制器内部故障仍需要独立安全措施。

本次仅修改本地代码、重建桥接并执行模拟测试，没有再次连接实机，也没有发送任何实机命令。软件回归与本地回环控制器可验证退出报文和错误处理，不能证明这台机器人的编码器/伺服故障已排除。恢复运动前仍须核查本次超速、软限位和编码器报警，再进行现场受控验收；不应直接通过自动清错恢复遥操作。

## 后续：初始回位完成后误报“退出停机未确认”

用户在启动遥操作时报告：双臂回位完成，随后准备子进程关闭驱动时等待 IDLE 超时，父进程因此阻止遥操作启动。错误来自上述新增的关闭确认，不是 RealSense 或回位轨迹失败。

本次仅被动监听 UDP 4730 端口，通过桥接解码函数解析已到达的控制器反馈；未调用 `tj_open`、清错、使能、停止或运动接口，未向控制器发送数据。3 秒收到 2773 帧，均为：

- 双臂 `state=0`、`error=0`、`low_speed=1`，但 `commanded_state=-1`。
- 各侧源计数从 626601 推进到 629601；左臂最大绝对速度 0.142951°/s，右臂 0.116146°/s，均低于确认阈值 0.5°/s。
- 采样期间单关节最大位置范围约 0.000111°。

固定 SDK 的 `FxRtCSDef.h` 将 `m_CurState` 标为 `ArmState`，`m_CmdState` 标为独立的指令状态。上次实现错误地额外要求 `commanded_state=0`，模拟设备也固定回显 0，导致测试没有覆盖真实控制器的 -1 值。对这批实测反馈检查原条件，2773 帧全部被该字段拒绝；修正后全部满足实际模式、错误码、低速及数值速度条件。

修正仅涉及两处运行代码：驱动移除错误的 `commanded_state=0` 条件，保留发送成功、新鲜度、源计数、实际 IDLE、错误码和速度检查。准备程序将“初始姿态准备完成”移到关闭确认成功之后，避免先报完成再报失败。测试模拟改为实际观测到的 -1，在已有双臂回位退出测试中覆盖此反馈值。

证据见 [被动采样摘要](tianji_shutdown_idle_feedback_20260916.json)。采样发生在用户运行之后，没有记录当时的下伺服报文及两秒内的切换时序；它确认了真实 IDLE 反馈会被旧条件持续误拒绝，不能用于证明先前异常旋转的控制器内部原因已经解决。
